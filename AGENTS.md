# Agent Instructions

## Release Intent, Versioning, and Workflow

Treat explicit release requests—such as “Mint a new release,” “Release this,” “Publish this as a new release,” “Create a new release,” or any clear equivalent—as authorization to carry out BuildVersion.Cli's full release workflow, including committing, pushing, tagging, and publishing as needed.

If the user has not clearly requested a release, or if the appropriate change category cannot be determined confidently, ask for clarification **before** committing, pushing, creating a tag, or publishing a release.

Only change BuildVersion.Cli's release version when the user has clearly requested that a release be published. Do not create a release-version tag during ordinary implementation, refactoring, bug-fixing, dependency updates, testing, commits, pushes, or pull-request preparation unless those actions are part of an explicitly requested release.

Choose the next version using these repository-specific rules:

- Minor, backward-compatible changes increment the patch component. Example: `10.0.1` → `10.0.2`.
- Moderate or breaking changes increment the middle component and reset the patch. Example: `10.0.1` → `10.1.0`.
- Increment the major component and reset the other components only when the newest supported .NET version changes. Example: `10.0.1` → `11.0.0`.
- Breaking changes alone do not justify a major-version increment in this repository. If multiple categories apply, use the highest applicable category.

BuildVersion.Cli uses MinVer in `src/Cli/Cli.csproj`; the lightweight `vX.Y.Z` Git tag is the authoritative package version. Do not add or manually update fixed `Version` or `AssemblyVersion` properties for a release. The CI `FileVersion` includes the GitHub run number and remains generated by the project. Some historical tags are annotated, but new release tags must be lightweight.

A clear release request authorizes this complete workflow:

1. Inspect the worktree, current branch, `origin`, current `develop`, recent commits, pull requests, and releases before making release changes.
2. Determine the next version from the rules above and verify that the tag and GitHub release do not already exist.
3. Validate the release-scoped changes using the repository's normal restore, Release build, test, and pack commands.
4. Create or reuse an appropriately named `feature/<short-description>` branch; do not commit release work directly to `develop`.
5. Commit all release-scoped changes using the repository's concise commit-message style, then push the feature branch.
6. Open a ready pull request against `develop` using recent title and body conventions, enable squash auto-merge, and monitor checks and review state.
7. Fix and push any issue that prevents the pull request from merging, then wait until it is merged.
8. Fast-forward local `develop` from `origin/develop`, prune deleted remote refs, and remove the merged local feature branch when appropriate.
9. Create the lightweight `vX.Y.Z` tag on the latest `develop` commit and push that tag to `origin`.
10. Publish a non-draft GitHub release named `vX.Y.Z - Description`, using concise release-note bullets consistent with recent releases.
11. Monitor the release-triggered `Deploy` workflow until the NuGet package is published successfully, fixing in-scope failures when possible.

Do not require separate confirmation for each Git or GitHub step after an unambiguous release command. Report the pull request, merge commit, tag, GitHub release URL, and NuGet publishing result when complete.
